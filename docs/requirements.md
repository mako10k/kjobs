# kjobs MVP 要件定義

文書状態: 基本設計への入力として受け入れ済み  
版: 0.1  
基準日: 2026-08-02  
対象計画: `plans/mvp.pert` の `REQUIREMENTS_DEFINITION`

## 1. 目的

`kjobs` は、依存関係と優先順位を考慮してシェルコマンドを実行し、失敗時の復旧と実行状況の確認を一つのシンプルな CLI で行える汎用ジョブ管理ツールとする。

主な利用者は、ローカル端末または単一ホスト上で、定型作業、ビルド、保守、データ処理などを再現可能に実行したい開発者・運用者である。

### 1.1 成功の定義

利用者が一つの宣言ファイルにジョブを記述し、次に行うべきジョブを確認または実行でき、成功・失敗・復旧・進捗を端末だけで追跡できることをMVPの成功とする。

### 1.2 想定利用者

- 開発者: ビルド、テスト、生成、リリース準備などの依存作業を実行する。
- 運用者: バックアップ、検証、保守など、失敗時に定型復旧を伴う作業を実行する。
- 自動化エージェント: JSON出力と安定した終了コードを利用して、非対話で次ジョブを選択・実行する。

### 1.3 主要ユースケース

1. 利用者がジョブ群を定義し、依存関係と設定ミスを実行前に検証する。
2. 利用者または自動化エージェントが、プロジェクト全体にとって優先すべき次ジョブを確認する。
3. `kjobs` が選択したシェルコマンドを実行し、結果とログを永続化する。
4. 失敗時に、制限付き再試行または定義済み復旧処理を行う。
5. 利用者が途中または終了後に、進捗、失敗理由、過去の実行を確認する。
6. 利用者が任意のテンプレートから、共通設定を持つジョブを定義する。

## 2. 基本方針

- ジョブ定義と実行状態を分離する。
- ジョブ定義を宣言的なプロジェクトファイルで管理する。
- 実行可能なジョブの列挙と、今優先すべきジョブの選択を分離する。
- 優先順位は依存関係、明示優先度、推定時間、クリティカルパス、利用可能リソースを考慮する。
- 優先順位計算には `perttool` の公開 Core API を利用し、`kjobs` 独自の順位計算を重複実装しない。
- 実行結果、標準出力、標準エラー、状態遷移を後から確認できるようにする。
- 非対話実行でも使える安定した終了コードと JSON 出力を提供する。

## 3. 用語

| 用語 | 意味 |
| --- | --- |
| Job | 一つの実行単位。基本的にはシェルコマンド |
| Run | 一つのジョブを一回実行した記録 |
| Workflow | 依存関係を持つジョブ群 |
| Ready | 依存条件を満たし、実行候補になった状態 |
| Recommended | Ready のうち、優先順位計算により次の実行対象として推薦された状態 |
| Recovery | ジョブ失敗後に実行する復旧処理 |
| Template | 変数を受け取り、ジョブ定義の雛形を生成する再利用可能な定義 |

### 4.1 CLI

CLI は、最低限次の操作を提供する。

```text
kjobs init
kjobs validate
kjobs job list
kjobs job show <job-id>
kjobs next
kjobs run [<job-id>] [--dry-run]
kjobs status [<job-id>]
kjobs history [<job-id>]
kjobs retry <job-id>
kjobs cancel <job-id>
kjobs template list
kjobs template show <template-id>
kjobs template apply <template-id>
```

- `kjobs run` でジョブ ID を省略した場合、現在 startable かつ recommended なジョブを実行する。
- 推薦が複数ある場合、既定ではその集合を表示し、並列数の設定範囲で実行する。対話入力を必須にしてはならない。
- すべての参照系コマンドは人間向けテキストと `--format json` を提供する。
- 破壊的または実行を伴う操作は `--dry-run` で、対象、順位選択理由、実行コマンド、復旧方針を確認できる。
- エラー時は短い要約、対象ジョブ、Run ID、次に取れる操作を表示する。

### 4.2 ジョブ定義

各ジョブは最低限、次の情報を持てるものとする。

- 一意で安定したジョブ ID
- 任意の説明
- 実行コマンド
- 作業ディレクトリ
- 環境変数名と値、または実行環境から継承する変数名
- 依存するジョブ ID
- 明示優先度
- 推定実行時間
- 必要リソースと数量
- タイムアウト
- 再試行方針
- 復旧方針
- 任意のテンプレート参照と入力値

定義ファイルの既定名は `kjobs.yaml` とする。環境変数の秘密値を状態表示やログへ平文で出力してはならない。秘密管理製品との連携は将来拡張とし、MVP では実行環境からの継承を基本とする。

### 4.3 コマンド実行

- ジョブの基本実行単位はシェルコマンドとする。
- 既定シェルを明示し、ジョブ単位で変更できるようにする。
- 標準出力と標準エラーは端末へストリームしながら Run ごとに保存する。
- 終了コード、開始・終了時刻、所要時間、終了理由を保存する。
- 正常終了条件は既定で終了コード `0` とし、許容終了コードを設定可能にする。
- タイムアウト、シグナル終了、起動失敗を通常の非ゼロ終了と区別して記録する。
- Ctrl-C 等による中断では子プロセスへ適切にシグナルを伝播し、Run を実行中のまま残さない。
- 同じジョブの重複同時実行は既定で禁止する。

### 4.4 優先順位と perttool 連携

`kjobs` のジョブ定義を正とし、優先順位計算時にジョブ、依存関係、状態、推定時間、明示優先度、リソースを `perttool` のプロジェクトモデルへ投影する。利用者に同じ内容を `kjobs.yaml` と `.pert` の二重で管理させない。

- `Ready` と `Recommended` を区別する。
- 実行対象は `perttool` の完全な結果に含まれる `startable_recommended_task_ids` 相当の開始許可を用いて決定する。
- 単なる依存解消済み、または推薦リストに含まれるだけでは自動実行しない。
- 推薦理由として、少なくとも依存関係、明示優先度、クリティカルパス、リソース競合の情報を表示できるようにする。
- 優先順位計算が不完全、入力不正、または連携不能の場合は自動選択を fail closed とし、明示 ID 指定による手動実行だけを許可する。
- `kjobs next --format json` は、Ready、Recommended、Startable、Blocked とその理由を機械可読で返す。

### 4.5 状態管理

ジョブの表示状態は最低限、次を区別する。

- `pending`: 未実行
- `ready`: 依存条件を満たした
- `running`: 実行中
- `retry_wait`: 再試行待ち
- `recovering`: 復旧処理中
- `succeeded`: 成功
- `failed`: 失敗し、自動処理が終了した
- `blocked`: 依存失敗などにより実行不能
- `canceled`: 利用者が中止した
- `skipped`: 明示的に実行対象外とした

状態更新は原子的に保存し、プロセス異常終了後に `running` のまま残った Run を検出して `interrupted` として回収できるようにする。ジョブの集約状態と個々の Run 履歴を混同しない。

### 4.6 再試行と復旧

再試行方針は、最大試行回数、待機時間、バックオフ、再試行対象となる終了コードまたは終了理由を指定できる。

復旧方針は、失敗したジョブに対して実行する一つ以上のシェルコマンドとして定義できる。処理順は次を基本とする。

1. 本体コマンドが失敗する。
2. 設定された復旧コマンドを実行する。
3. 復旧成功後、方針に応じて本体を再試行するか、復旧済み失敗として停止する。
4. 復旧失敗時は本体失敗と復旧失敗の両方を記録して停止する。

- 復旧コマンドの成功だけで元ジョブを `succeeded` にしてはならない。
- 無限再試行を禁止し、総試行回数に上限を設ける。
- 本体と復旧処理のログおよび終了結果を分離して確認できるようにする。
- 復旧処理自身への入れ子の復旧は MVP では扱わない。
- 将来、別ジョブやサブワークフローを復旧処理として参照できる拡張余地を残す。

### 4.7 ジョブテンプレート

- テンプレートは任意機能とし、テンプレートなしでもすべてのジョブを定義できる。
- テンプレートはコマンド、作業ディレクトリ、環境変数、タイムアウト、再試行、復旧、リソースなどの既定値を持てる。
- テンプレート入力には名前、型、必須性、既定値、説明を定義できる。
- 適用後の実効ジョブ定義を `validate`、`show`、`dry-run` で確認できる。
- 未定義変数、未知の入力、循環継承は検証エラーとする。
- MVP では一段のテンプレート適用のみとし、多段継承は扱わない。

### 4.8 状況・進捗表示

`kjobs status` は最低限、次を表示する。

- ジョブ総数と状態別件数
- 現在実行中のジョブ、開始時刻、経過時間
- 次に実行可能・推薦されるジョブ
- 失敗またはブロックされたジョブと理由
- ワークフロー全体の完了率

完了率は既定で `succeeded / 対象ジョブ数` とし、推定時間による加重進捗は参考値として明示的に区別する。端末再描画型の常時ダッシュボードは MVP の必須要件にせず、必要に応じて `--watch` を追加できる設計とする。

### 4.9 永続化と排他

- プロジェクトローカルな状態ディレクトリ `.kjobs/` に Run、状態、ログを保存する。
- 実行中の状態更新には排他制御を行い、複数の `kjobs` プロセスによる競合を防ぐ。
- 定義ファイル変更後も過去 Run のジョブ ID、実行コマンド、実効設定を追跡できるスナップショットを保存する。
- `.kjobs/` を削除しても宣言的なジョブ定義は失われないが、履歴と実行状態は失われる旨を明記する。

## 5. 非機能要求

| ID | 分類 | 要求 |
| --- | --- | --- |
| `KJ-NFR-001` | 移植性 | MVPはLinuxとmacOSで動作し、WSLはLinuxとして扱う。 |
| `KJ-NFR-002` | 安全性 | 秘密値を通常出力、JSON、保存設定、診断へ平文で露出しない。 |
| `KJ-NFR-003` | 一貫性 | 状態更新を原子的に保存し、同一ジョブの既定の重複実行を防ぐ。 |
| `KJ-NFR-004` | 再現性 | 同じ定義と状態から同じ優先順位入力と選択結果を得る。 |
| `KJ-NFR-005` | 可観測性 | すべてのRunに一意なIDを付け、本体と復旧の記録を追跡できる。 |
| `KJ-NFR-006` | 互換性 | 定義、状態、JSON出力に形式バージョンを持たせる。 |
| `KJ-NFR-007` | 応答性 | `list`、`status`、`next` はジョブ本体を起動せず応答する。 |
| `KJ-NFR-008` | 自動化 | 非対話環境で安定した終了コードを返し、入力プロンプトを必須にしない。 |

- ランタイム: `perttool` の現行公開 API に合わせ Node.js 22 以上を第一候補とする。
- 安全性: シェルコマンドは信頼済みのローカル定義として扱い、外部入力を無検証でテンプレート展開しない。

## 6. MVP の範囲

MVP に含めるもの:

- 単一プロジェクト、単一ホストでの実行
- YAML によるジョブ、依存関係、優先度、リソース、再試行、復旧の定義
- `perttool` による次ジョブ推薦
- ローカルプロセス実行、タイムアウト、キャンセル
- ローカル状態・ログ・履歴
- 一段のジョブテンプレート
- テキストおよび JSON の状態表示
- 設定可能なローカル並列実行

MVP に含めないもの:

- 分散実行、リモートエージェント、クラスタスケジューラ
- Web UI、常駐サーバ、マルチユーザー認証
- cron 相当の日時スケジュールやイベント監視
- コンテナの自動作成
- 秘密情報ストアの内蔵
- 復旧ワークフローの入れ子や動的 DAG 生成
- 厳密な大域最適スケジューリングの保証

## 7. perttool の SDK 化方針

現時点では、別パッケージへの SDK 切り出しは行わない。`perttool 0.5.0` は MIT ライセンスであり、npm パッケージのルートから `analyzeDocument`、`selectNextTasks`、パーサ、検証器、分析結果型などを公開しているため、`kjobs` はまず通常のライブラリ依存として利用できる。

`kjobs` 側には薄い `PriorityProvider` 境界を設け、次を担当させる。

1. `kjobs` のジョブと実行状態を `perttool` の入力モデルへ変換する。
2. `perttool` の Core API を呼び出す。
3. 完全性と開始許可を検証する。
4. 推薦集合と理由を `kjobs` の型へ変換する。

これにより、CLI サブプロセス呼び出しや `.pert` の二重管理を避けつつ、将来の実装差し替えも可能になる。

次のいずれかが実際に問題になった時点で、`perttool` 側の純粋な優先順位機能を `@perttool/core` のような SDK パッケージへ分離する。

- 公開パッケージが CLI・編集機能を含み依存サイズや起動時間の障害になる。
- `kjobs` が必要とする構造化入力 API がなく、文字列の `.pert` 生成に依存する。
- CLI と Core のリリース周期を分離する必要がある。
- Node.js 以外から安定して呼び出す必要がある。
- 公開 API の互換性保証を CLI とは別に管理する必要がある。

SDK 化する場合も、順位アルゴリズムを複製せず、純粋なモデル・検証・分析・推薦・型定義のみを Core に移し、ファイル I/O、CLI 表示、編集、安全書き込みは `perttool` 本体に残す。

## 8. MVP 受け入れ条件

1. `AC-01`: 三つ以上の依存関係付きジョブを定義し、`validate` で未知参照、循環、必須値不足を検出できる。
2. `AC-02`: `next` が Ready、Recommended、Startable を区別し、選択理由をテキストとJSONで表示できる。
3. `AC-03`: `run` が推薦ジョブを実行し、出力、終了コード、所要時間、終了理由を保存できる。
4. `AC-04`: 依存ジョブ成功後にのみ後続ジョブが実行可能になる。
5. `AC-05`: リソース競合または並列数上限があるとき、同時開始できないジョブを自動実行しない。
6. `AC-06`: 失敗ジョブに対して設定回数の再試行と復旧コマンドを実行し、上限で停止できる。
7. `AC-07`: 復旧失敗と本体失敗を別の記録として履歴表示できる。
8. `AC-08`: テンプレート入力を検証し、生成した実効ジョブを実行前に確認できる。
9. `AC-09`: 異常終了後の孤児Runを検出し、`interrupted` として回収できる。
10. `AC-10`: テキスト表示とバージョン付きJSON表示が同じ状態を表現する。

## 9. 初版で固定しない設計事項

実装着手時に基本設計で確定する。

- YAML の厳密なスキーマとテンプレート式の構文
- 状態ストアを SQLite とするか、原子的 JSON ファイル群とするか
- 並列実行時の端末ログ表示方式
- `perttool` へ構造化モデルを直接渡すか、一時的な Grammar 5 文書へ投影するか
- 明示 ID 指定時に、依存未達やリソース不足を強制実行できる管理者オプションを設けるか

これらは基本設計タスクで決定する。いずれの選択も、第4節、第5節、およびMVP受け入れ条件を弱めてはならない。

## 10. 要件変更管理

- 要件の追加・変更・削除では、要求ID、影響する受け入れ条件、`plans/mvp.pert` の見積りまたは依存関係への影響を確認する。
- MVP境界を広げる変更は、既存MVPの完了条件と分離できるかを先に評価する。
- `perttool` の推薦意味論または公開APIが変わる場合、`KJ-FR-004`、`KJ-FR-005`、`KJ-NFR-004` を再確認する。
